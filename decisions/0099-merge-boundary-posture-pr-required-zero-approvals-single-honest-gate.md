# 0099. Merge boundary is a PR-required ruleset with zero approvals, and layer 1 is reshaped to gate only on what that proves

## Context

0095 permanently descoped boundary provisioning, so the preflight was left checking for a boundary nobody would ever create. An independent audit then established by live probe that this repo has NO branch ruleset at all (gh api rules/branches/main returns []), that the acting credential is the owner SatanshuMishra with permissions.admin true, and that the gh merge-deny shim is not wired into PATH (command -v gh resolves to /opt/homebrew/bin/gh). The audit separately confirmed that no coded path in the engine or CI can merge without a human (merge-policy.mjs:1-13 returns only human-gated; receipts.yml has no merge step; the pinned enforcer requests pull-requests:write only for its report comment), so the exposure is capability, not code. Reading the gate revealed it carries FOUR gating invariants, not one: identity must equal a configured machine user (merge-boundary-preflight.mjs:153), the repository must report admin exactly false (:171), the base branch must require at least one approving review with require_last_push_approval exactly true (:236-241), and the rule must bind to an active repository-owned ruleset (:262). The first three are unsatisfiable by construction in a single-owner personal repo: the owner is structurally admin on their own repo, and GitHub forbids self-approval, so a lone human account can never satisfy a one-approval requirement on its own pull requests. The gate had been designed for a two-identity world, and descoping the machine user removed the ground under three of its four checks at once. Leaving it unchanged would make it halt on three of four checks forever, which is the permanent-halt posture rather than a working gate.

## Options

- Reverse the descoping and provision a machine user or GitHub App with write-not-admin, set required approvals to 1, leaving all four invariants satisfiable and layer 1 working unmodified. This is the ONLY shape in which the server enforces a human merge gate; rejected because it contradicts the explicit ruling of no approvals and reverses 0095.
- Keep layer 1 unchanged and accept that it halts every run forever, treating the boundary as permanently unusable. Rejected: the user chose to provision rather than to halt.
- Delete layer 1 alongside layer 2 and record that merge is client-side gated only. Rejected: the audit's counter holds, since this converts a refusal to fan out against an unprotected base into silently fanning out against one, and no-direct-push-to-base is still worth proving before dispatch.
- Strip layer 1 down to ruleset-existence only, deleting the identity, admin and review checks outright rather than demoting them. Rejected: discards the observations that would reveal a later change in the credential situation.

## Outcome

Three-part ruling. FIRST, the human (never the agent) creates a repository ruleset on main: pull_request rule required, required_approving_review_count exactly 0, bypass_actors empty, enforcement active. Zero is deliberate and not a weakening to be corrected later - on a single-maintainer repo any value of 1 or more would make the owner permanently unable to merge their own pull requests. Empty bypass is the load-bearing element: rulesets apply to admins, so it stops even the owner from pushing to main outside a pull request. The agent must never create or edit this ruleset, on the gate's own logic at merge-boundary-preflight.mjs:270 that write access to the boundary would let the engine edit the boundary it rests on. SECOND, layer 2 - the reconcile subagent's re-run of the preflight at mitosis.js:3720-3721, the readBoundaryPreflightVerdict reader at :127-160, the boundaryPreflight schema at :1357-1366 and the call at :3748 - is DELETED. It is unsatisfiable as documented, silent on its dominant failure path, and corroborates through the same physical file via the same symlink it is meant to corroborate, so it adds no independent trust base. THIRD, layer 1 survives as the single gate but is reshaped to assert only what this posture actually proves: it gates on a pull_request rule existing and on that rule binding to an active repository-owned ruleset, keeps the bypass list as a documented human-confirmed gap, and DEMOTES identity, admin and review to non-gating observations. The review check is renamed off base-branch-requires-an-approving-review, because keeping that identifier while accepting zero approvals would print a PASS whose message asserts something untrue - exactly the theatre the audit warned against. Its pass text must state plainly that changes can enter only by pull request, that review is NOT server-required, and that merge therefore remains gated only by client-side denies and the human at the keyboard. ACCEPTED AND RECORDED CONSEQUENCE: with zero required approvals no server-side mechanism distinguishes an agent merging a pull request from a human merging one; required status checks, CODEOWNERS and environment reviewers all either reduce to at-least-one-approval or do not apply to pull request merges. The property bought is no-direct-push-to-base, server-enforced against everyone including the owner. The upgrade path to a genuine server-side human merge gate remains a second identity, and is deliberately not taken.
