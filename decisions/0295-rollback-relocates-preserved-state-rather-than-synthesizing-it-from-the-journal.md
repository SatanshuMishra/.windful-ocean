# 0295. Rollback relocates state preserved on disk rather than synthesizing it from the journal, and authentication is rejected as the wrong axis

## Context

0294 adopted a design pass on the theory that the root cause was unauthenticated, ungated control files, and named the F1 remedy the round-4 owner had identified: derive created from linkTargetFor(name) rather than reading it from the journal. The design pass falsified both. Measured: deriving created turns the ownership test at cutover.mjs:616 into readlink(path) === linkTargetFor(name), which is a predicate about current STATE rather than about AUTHORITY. After a legitimate cutover every promoted entry already satisfies it by construction, so ours is true for all eleven names for anybody, and restoreLink still reaches placeLink, which passes an attacker-chosen target unchecked to symlinkSync at :430. The hooks-to-attacker-directory exploit survives the recommended fix. This is the third proposed remedy in this unit to be wrong: round 3's written correction too strong, round 4's reviewer proposal too strong, round 4's cheaper proposal too weak. The design pass also established the threat model honestly - a full-uid attacker can edit cutover.mjs itself and no scheme defends that, so the attacker who matters is a constrained writer that cannot silently write ~/.claude/hooks/** but writes ~/.claude/CUTOVER freely today, since CUTOVER, LIVE and the aside namespace match neither protect-claude-config.sh:20-21 nor guardpath at block-destructive-bash.sh:17. An ungated write is laundered into a gated effect by a verb the human runs on purpose.

## Options

- Preserve-and-relocate: apply moves every non-absent entry aside, link or real, and rollback restores only by rename of a derived aside plus unlink, so the prior target is never named in JSON - ADOPTED. Authenticated control files, a MAC over canonical journal and receipt bytes with the key in Keychain - rejected on over-strength: a missing key refuses every rollback on a fresh machine, on the one path whose purpose is to work when things have gone wrong, and it converts the hand-edit the tool itself instructs at cutover.mjs:215 and :581 into a permanent refusal; it authenticates integrity rather than authority, closes neither F3 nor F5, and leaves replay open unless bound to liveSha, itself a known over-strength trap. Gate-and-degrade alone, refusing to synthesize any link and printing relink-by-hand - rejected as the main path because nine of eleven entries are links here so rollback would restore nothing and emit nine manual instructions; retained only as the fallback branch when a corroborating aside is missing.

## Outcome

Adopted. The governing property is that rollback must never synthesize prior state from a description of it; it relocates prior state preserved on disk. symlinkSync of a journal value leaves the rollback path entirely, and the journal degenerates from a set of instructions into an enumerable, disk-corroborated index. Authentication is rejected as the wrong axis: a MAC answers whether bytes were modified when the question is whether the file has authority to name a syscall argument, and the answer is that it should not need trusting at all. Seven invariants I1-I7 are stated in artifacts/2026-08-08-cutover-control-file-invariants.md, each with its forbid-set, its permit-set, and the realistic pre-state that falsifies it if stated too strongly; an invariant with no permit-set is treated as unfinished. The permit-sets are load-bearing because nine of the eleven entries the verb touches are outward symlinks on this machine, confirmed by direct readlink, which is the trap that caught rounds 2, 3 and 4. Two consequences are accepted knowingly: nine extra depth-1 aside entries after cutover with partial-apply resumption messaging reworked, and I5's monotone guardrail discovery, which deletes the derived suppressor, inverts protect-claude-config.test.mjs:188 and :289 - those two tests encode the suppression F3 exploits - and begins prompting on five foreign guarded subtrees. Monotonicity is intrinsically over-strength-proof: its worst case is more prompts, never a refused deployment. I6 is stated honestly as porous defence-in-depth, since guardverb misses an interpreter one-liner that opens a file for writing, so I1 through I3 must never depend on it. This decision SUPERSEDES 0294 on one point: 0294 recorded the already-linked dangling-entry blocker as separate contained work, and it is in fact a precondition, because under I2 a misclassified entry gets no aside and therefore no rollback authority, making a dangling entry unrecoverable rather than merely wrong.
