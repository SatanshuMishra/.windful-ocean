# 0517. Repoint the continuity ledger rule fully rather than only fixing the two names that dangle

## Context

A survey found the continuity ledger rule naming two skills that do not exist, both backtick-fenced and both sitting next to dispatch language. The name-integrity census could not ship until they resolved, because a red census cannot merge and that census is forbidden from repairing anything it censuses. The damage was wider than the names: the file described the superseded file-ledger layout in the repository while the live system writes to the plugin's own store, and the implementer then found it asserting machinery that was never built. It claimed completion criteria could never be amended after creation when an amend tool exists, claimed a session-start scan flags stale threads when no staleness logic exists anywhere, and claimed over-cap content is demoted to the session log when the cap check simply throws.

## Options

- Fix only the two dangling skill names so the census goes green
- Repoint the names and correct the storage description and every provably false mechanism claim
- Point the rule at the legacy skills that match the layout it already describes

## Outcome

Repoint fully. Naming the legacy skills would have made a live rule point at the superseded path, and a names-only fix would have left a rule that resolves while still describing storage that does not exist. The repair is bounded by proof rather than by suspicion: ten sites were corrected each against a cited mechanism, and five passages that read as stale were reported untouched rather than rewritten, because turning unproven suspicion into confident prose is the same failure the repair was undoing. The sharpest unresolved one is that threads appear to be worked while already paused, which would hollow out the rule's claim that an active thread at session start is an anomaly.
