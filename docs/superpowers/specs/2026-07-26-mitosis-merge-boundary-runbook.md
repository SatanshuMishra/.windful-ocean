## 1. What this establishes and why both halves are required

Earlier attempts to enforce "the engine never merges" lived entirely client-side: a `PreToolUse` shell hook that pattern-matched merge-shaped commands, and narrowing the engine agent's own tool permissions. Both were torn down. A pattern-matched hook is fail-open by construction — it can only block the specific command shapes someone thought to enumerate, and `git`/`gh`/the GitHub REST and GraphQL APIs offer more ways to merge a branch than any finite pattern list can cover. A permission narrowing is undecidable in the same sense — deciding, for an arbitrary future command or API payload, whether it constitutes "a merge" is not a problem client-side tooling can solve in general. Both layers depend on the engine's own client behaving correctly; neither is a boundary in the sense of being unbypassable by the thing it is meant to constrain.

The replacement moves the boundary to the one party that is authoritative over merges regardless of what any client does: the GitHub server itself. Two components, together, make that boundary complete:

1. A **ruleset** on the protected base branch. A ruleset is GitHub's mechanism for enforcing rules — such as "every change must go through a pull request" — on a set of branches, replacing the older "branch protection rules" feature. This runbook's ruleset requires a pull request with at least one approving review before a merge into the base branch is possible, with an empty **bypass list** (defined in Section 4: the set of users, teams, or roles that are exempted from the ruleset's rules).
2. A **separate machine-user identity** — its own GitHub account, distinct from any human's own account — that the engine authenticates as via a personal access token (PAT).

Neither half alone is a boundary:

- A ruleset alone, if the engine runs under a human's own admin/owner identity, is fiction. Admin accounts are the identity most commonly (and often accidentally) left on a bypass list, since that was the default behavior of the older branch-protection-rules feature; even with a scrupulously empty bypass list, an admin identity is one credential away from being used to both open and merge the same change.
- A machine-user identity alone, without a ruleset, is also fiction. Nothing stops a plain collaborator account from pushing straight to the base branch, or from approving and merging its own pull request, if no rule requires a pull request or a review in the first place.

Together, the ruleset forces every change through a pull request with a required approval, and the machine-user identity closes one path to a rubber-stamped merge: GitHub does not allow the author of a pull request to approve their own pull request — "Pull request authors cannot approve their own pull requests" ([GitHub Docs: Approving a pull request with required reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews)). This holds regardless of the author's own role on the repository, is stable across GitHub Enterprise versions, and is not plan-dependent. The same page documents an extension of the rule to Copilot: an author cannot approve a pull request raised by Copilot if that author was the one who assigned Copilot to the underlying issue.

Blocking self-approval is necessary but not sufficient on its own to turn "requires 1 approval" into "requires a human." Self-approval-blocking and bypass-emptiness are two independent controls, and the boundary needs both: an account holding the Admin role, or any custom role granted the ability to bypass branch protections, can merge a pull request with zero approvals — self-authored or not — unless bypassing is explicitly disallowed on the ruleset ([GitHub Docs: About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). Because the engine's identity is the PR author on every train PR, the self-approval rule closes the approval path; the empty bypass list and the "Do not allow bypassing the above settings" toggle configured in Section 4 close the merge-without-approval path. Neither control alone is the boundary — both together are. This is why the machine user and the ruleset's bypass configuration are both load-bearing, in tandem rather than independently.

Ruleset and bypass-list background: [GitHub Docs: About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

## 2. Create the machine user

Create a second, standalone GitHub account — its own username, its own email, its own credentials and two-factor authentication — that the engine authenticates as. This must not be the human operator's own account under a different token; the self-approval rule in Section 1 only helps if the PR author is genuinely a different account than any human reviewer. Many teams give the account a recognizable bot-style handle, e.g. `<org>-mitosis-bot` (placeholder pattern only — pick a real handle at apply time and do not record it in any committed file).

Add the account to `<ORG>/<REPO>` as a collaborator (or organization member, if `<ORG>` is an organization) with role **Write**.

For a repository owned by an organization, GitHub's repository role hierarchy, from least to most privileged, is Read < Triage < Write < Maintain < Admin ([GitHub Docs: Repository roles for an organization](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization)) — see below for the different model that applies if `<ORG>/<REPO>` is a personal-account repository instead. Write is the lowest role in that hierarchy that includes both push access to non-protected branches and the ability to open and manage pull requests — exactly what the engine needs to (b) push branches and (c) open/update PRs, and nothing more. Read and Triage do not include push access at all, so they are insufficient. Maintain and Admin are both excluded deliberately:

- **Admin** would let the engine's own identity edit or delete the ruleset created in Section 4, change branch protection, or manage other collaborators' access — i.e., dismantle its own boundary. Granting Admin to the engine's identity directly defeats the "GitHub server is the boundary" property this runbook establishes.
- **Maintain** adds repository-settings-adjacent capabilities (label/milestone management, and in some configurations broader merge controls) the engine never needs; it widens the blast radius of a compromised token for no operational benefit.

A ruleset's "require a pull request before merging" rule (Section 4) blocks direct pushes only to branches matching the ruleset's target pattern (the protected base branch). Write-level push access to other branches — the topic/feature branches the engine actually pushes to when opening each PR in the train — is unaffected, so Write remains sufficient even after the ruleset is in place.

Verified: the five-role hierarchy above applies only to organization-owned repositories. If `<ORG>/<REPO>` is owned by a personal account instead, GitHub documents a simpler, two-level model — the repository owner, and everyone else added as a collaborator — with no intermediate Read/Triage/Write/Maintain distinction: "In a private repository, repository owners can only grant write access to collaborators. Collaborators can't have read-only access to repositories owned by a personal account" ([GitHub Docs: Permission levels for a personal account repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)). Practical consequence for this runbook: on a personal-account repository, any non-owner collaborator is always effectively Write — there is no separate Write role to select, and no way to under- or over-grant relative to it. The boundary's non-admin requirement (Section 1: the machine user must not be able to dismantle its own ruleset) is satisfied simply by the machine-user account not being the repository's owner; confirm at apply time only that `<ORG>/<REPO>`'s owner is the human operator's own account, not the machine user's.

Cost/seat note: this document is committed inside a public repository, so its own placeholders are mandatory regardless of billing; separately, if the target `<ORG>/<REPO>` this runbook is applied to is a **private** repository inside an organization on a paid plan (GitHub Team or GitHub Enterprise Cloud), adding the machine user as a member typically consumes a paid per-seat license, while GitHub Free-tier personal-account repositories do not carry an explicit per-collaborator charge. **Needs confirmation at apply time:** whether adding an outside collaborator (rather than a full organization member) to a specific repository consumes a seat under the org's current billing plan — GitHub's seat-billing rules for collaborators differ by plan and have changed over time; check the organization's Settings > Billing before adding the account if `<ORG>` turns out to be a paid organization.

## 3. Mint the PAT

Prefer a **fine-grained personal access token (PAT)** over a classic PAT. A fine-grained PAT is scoped to specific, named repositories and specific, named permissions (e.g., "Contents", "Pull requests"), each set to an explicit access level (no access / read-only / read and write). A classic PAT instead grants broad, OAuth-style scopes (e.g., the entire `repo` scope) across every repository the account can see, which is far more than this engine needs. Reference: [GitHub Docs: Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Steps: log in to github.com **as the machine user**, not the human operator's own account. Navigate Settings -> Developer settings -> Personal access tokens -> Fine-grained tokens -> Generate new token. Set "Repository access" to "Only select repositories" and select `<REPO>`.

Grant exactly these repository permissions and nothing else:

| Capability needed | Fine-grained PAT permission | Required access level |
|---|---|---|
| (a) clone / fetch | Contents | Read-only (superseded by the next row if the same token also pushes) |
| (b) push branches | Contents | Read and write |
| (c) open and update pull requests | Pull requests | Read and write |
| (d) read CI status (workflow-run conclusion) | Actions (not "Checks" and not "Commit statuses" — see callout below) | Read-only |
| always included automatically | Metadata | Read-only |

Do **not** grant: Administration, Repository rulesets, Secrets, Webhooks, Environments, Deployments, or any other permission grouped under repository administration or security configuration in the token UI. Actions needs explicit read/write care now that row (d) above grants it: grant Actions at **Read-only, never Read and write**. Read and write additionally allows cancelling, rerunning, approving, or force-cancelling workflow runs, deleting artifacts/caches/logs, and disabling, enabling, or dispatching workflows ([GitHub Docs: Permissions required for fine-grained personal access tokens — Actions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens?apiVersion=2022-11-28#actions)) — none of which the ship stage's read-only CI poll needs, and all of which would let the token holder interfere with the very CI run the boundary depends on. Do not read "Actions" appearing in this table as license to grant it broadly; it is admitted here at Read-only and nothing higher. Repository rulesets in particular must never be granted write access — that would let the token holder edit or delete the very ruleset built in Section 4. If in doubt about a permission not listed above, apply the test "would this let the token change repository settings, security configuration, or CI configuration" and exclude it if the answer is yes or unclear — this is also the test that rules out Actions: Read and write.

Verified: a "Checks" permission is not currently assignable to a fine-grained PAT at all — GitHub Support has stated that only a GitHub App identity can access the Checks API, and that this PAT capability was deliberately disabled. This is confirmed via a GitHub-hosted community-forum thread quoting Support, not a docs.github.com page, and is labeled as such: [GitHub Community Discussion #129512](https://github.com/orgs/community/discussions/129512). This constraint turns out not to be engine-breaking, and is kept here as background rather than as a live threat — see the RESOLVED callout below. Separately, a fine-grained PAT can read CI results through the older Commit Statuses API where a project's CI reports through commit statuses, gated by the "Commit statuses" permission at Read-only — but, per the callout below, that is not the path this engine's own CI poll takes, so it is not part of the grant reflected in the table above.

> RESOLVED (codebase-verified): the mitosis engine's CI-status read lives at exactly one place — the ship stage's prompt, built at `mitosis.js:4586-4599` and dispatched to an `implementer` subagent, with the CI-wait instruction itself at `mitosis.js:4596`. It resolves a run id via `gh run list` scoped to the target repo and the integration branch, requesting `--json databaseId`; polls with `gh run view ... --json status` until `status` reads `completed`; then reads the terminal result once with `gh run view ... --json conclusion`, treating `conclusion=success` as CI GREEN and any other terminal conclusion as CI RED. Both `gh run list` and `gh run view` correspond to the GitHub Actions Workflow Runs REST API — `GET /repos/{owner}/{repo}/actions/runs` and `GET /repos/{owner}/{repo}/actions/runs/{run_id}` — a third surface distinct from both the Checks API and the Commit Statuses API discussed above. On a fine-grained PAT this surface is gated by the "Actions" repository permission at Read-only, not "Commit statuses" and not "Checks" ([GitHub Docs: Permissions required for fine-grained personal access tokens — Actions](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens?apiVersion=2022-11-28#actions)). The engine holds no token-scoping, `GH_TOKEN`-override, or PAT-selection logic of its own — a grep across `mitosis.js` and `.claude/lib/superpowers-parallel/*.mjs` finds zero occurrences of `GH_TOKEN`, `GITHUB_TOKEN`, or `gh auth` — so every `gh` call the engine issues, including this one, runs under whichever identity the process is already authenticated as (the environment-variable setup in this section). That is what makes the Actions: Read-only grant in row (d) above load-bearing, not optional: the "Checks is unavailable to fine-grained PATs" finding above, while still true, never actually threatened this engine, because the engine was never calling the Checks API — or the Commit Statuses API — in the first place. Omitting Actions: Read is a real failure mode of its own; see Section 8.

Expiry guidance: verified — a fine-grained PAT's expiry is configurable up to 1 year, and a no-expiration option also exists ([GitHub Docs: GitHub's programmatic access credential types](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/github-credential-types)). Set the shortest expiry that is operationally tolerable (for example 90 days) and calendar a rotation before it lapses; do not rely on the no-expiration option for this token. Separately, an organization can enforce a maximum-lifetime policy on fine-grained PATs: the default maximum is 366 days, and organization admins may configure any value between 1 and 366 days ([GitHub Docs: Setting a personal access token policy for your organization](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/setting-a-personal-access-token-policy-for-your-organization)). A token that is non-compliant with the organization's policy is rejected at call time, not proactively revoked — confirm at apply time whether `<ORG>` has set a policy stricter than this runbook's own expiry choice, since a stricter org policy simply shortens the effective expiry rather than blocking token creation. An expired or rejected token fails **closed** — the engine simply cannot push or open PRs — which is the safe failure direction; see Section 8.

Where the engine reads the token from: an environment variable local to the process that runs the engine, sourced from the operator's shell or secret manager at process start. Verified: `GH_TOKEN` takes precedence over `GITHUB_TOKEN`, and both override any previously stored `gh` credentials ([GitHub CLI manual: Environment variables](https://cli.github.com/manual/gh_help_environment)). Use `GH_TOKEN` for this token. The `gh auth login` manual separately recommends `GH_TOKEN` specifically for fine-grained PATs ([GitHub CLI manual: gh auth login](https://cli.github.com/manual/gh_auth_login)), though the documentation does not explain why fine-grained PATs are called out over classic ones. Never commit the token to any file, never place it in a checked-in `.env`, and never let it appear in engine logs or transcripts.

## 4. Create the ruleset

Navigate to the base branch's protecting ruleset in the target repository: Settings -> Rules -> Rulesets -> New ruleset -> New branch ruleset. Needs confirmation at apply time: GitHub periodically renames settings sub-pages; if this exact path does not match, look for "Rulesets" or "Branch protection rules" under the repository's Settings > Code and automation section.

Configure:

- **Name**: any descriptive name, e.g. `protect-base-require-review`.
- **Enforcement status**: Active. Not Disabled (rule exists but does nothing) and not Evaluate (dry-run/report-only mode that logs would-be violations without blocking them).
- **Target branches**: Include by pattern -> `<BASE_BRANCH>` (the specific protected base, e.g. what would be `main`).
- **Bypass list**: leave **empty**. Do not add "Repository admin", "Organization admin", any team, or any specific account. This is the single field most likely to be pre-populated by GitHub's UI defaults or carried over from habits formed under the older branch-protection-rules feature (which historically exempted admins by default) — explicitly check for, and remove, any pre-populated entry.
- **Rules** -> enable "Require a pull request before merging." Set "Required approvals" (label needs confirmation at apply time; also seen as "Required number of approvals before merging") to at least 1.
- Within that same rule there is a setting commonly labeled "Do not allow bypassing the above settings" (needs confirmation at apply time: exact current label text, and whether this toggle maps to any distinct, separately-readable API field — no docs sentence found confirms or denies this; see Section 7). Ensure it is enabled. Its function is to make the "require pull request" rule bind even for actors who might otherwise carry elevated repository access outside the bypass-actors mechanism, so treat it as a second, independent control alongside the empty bypass list above — verify both, not just one. See Section 1 for why this bypass configuration and the platform's self-approval block are two independent controls, both required together; neither substitutes for the other.

Explicitly: if the human operator's own account holds the Admin role on `<ORG>/<REPO>` (typical for the repository owner), that account must **not** appear anywhere in the bypass list. A ruleset is decorative for any account left on its bypass list, regardless of what role that account otherwise holds.

References: [GitHub Docs: About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [GitHub Docs: Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), [GitHub Docs: Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets).

## 5. Merge strategy — a decision the human must make

Terms: a **merge commit** creates one new commit with two parents on the base branch and leaves every commit from the PR branch on the base with its original SHA unchanged. A **squash merge** collapses every commit in the PR into a single new commit applied to the base; none of the PR's original commit SHAs survive. A **rebase merge** replays each of the PR's commits individually onto the tip of the base; each replayed commit gets a new SHA even though its diff content is unchanged, because its parent linkage changed.

This matters specifically for a stacked PR train because of how GitHub retargets a child PR after its parent merges. Verified, quoted exactly: "If you delete a head branch after its pull request has been merged, GitHub checks for any open pull requests in the same repository that specify the deleted branch as their base branch. GitHub automatically updates any such pull requests, changing their base branch to the merged pull request's base branch" ([GitHub Docs: Creating and deleting branches within your repository](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-and-deleting-branches-within-your-repository)). The trigger is explicitly the **deletion** of the merged head branch, not the merge itself — merging alone does not retarget anything. If the engine's PR flow does not delete each unit's integration branch after merge, retargeting never fires, and the child PR is left pointed at a branch that still exists but received no further commits — a different, quieter failure mode worth checking for separately.

`[unverified]`: GitHub's documentation is silent on multi-hop / stacked-PR cascades — the retargeting behavior above is confirmed for a single parent-to-child hop, and its absence was confirmed across three related documentation pages checked for any mention of cascading through a chain of more than two stacked PRs. Any reliance on cascade behavior propagating correctly through a longer stack is an unverified assumption about this runbook's specific use case, not a documented GitHub guarantee.

| Strategy | What happens to the parent PR's commit SHAs | Effect on the child PR once GitHub auto-retargets it | Restack cost |
|---|---|---|---|
| Merge commit | Preserved exactly, plus one new merge commit | The child's history already contains the exact commits now on the new base; its diff and merge-base stay clean | None — the child PR continues to show only its own real diff |
| Squash merge | Discarded; replaced by one new commit with a new SHA | The child's recorded parent commits are the old, pre-squash ones, which are not reachable in that form from the new base; git sees the histories as diverged | The child branch must be explicitly rebased onto the new base tip; every PR further down the train inherits the same requirement |
| Rebase merge | Discarded; every commit replayed with a new SHA | Same failure mode as squash — the child's recorded parents no longer match anything reachable on the new base | Same as squash — explicit restack required |

This runbook does not pick a strategy; that decision belongs to the human, weighed against the target repository's own conventions and the mitosis engine's own use of commit SHAs. Note one project-specific consequence worth weighing (this is inference about this codebase's own architecture, not a claim about GitHub, so no external citation applies): if the engine's checkpoint or provenance tracking keys any state on a parent unit's pre-merge commit SHA, squash and rebase merges invalidate that keyed state on every merge, independent of whether the visible PR diff also breaks. A merge-commit strategy avoids both costs at the price of a non-linear base-branch history.

## 6. The CI gotcha: `pull_request` trigger defaults exclude `edited`

Verified: GitHub Actions' `pull_request` trigger, when no `types:` key is given, runs only for activity types `opened`, `synchronize`, and `reopened` ([GitHub Docs: Events that trigger workflows — pull_request](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#pull_request)).

Verified: the auto-retarget behavior described in Section 5 fires a `pull_request` event with activity type `edited`. GitHub's own webhook-event data source describes `edited` as "The title or body of a pull request was edited, or the base branch of a pull request was changed" ([GitHub Docs: Webhook events and payloads — pull_request](https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request)). `[unverified]`: the exact nested key names under a `changes.base` object (for example, whether the prior ref and SHA are recorded as `changes.base.ref.from` / `changes.base.sha.from`) could not be quote-grounded against docs.github.com in this pass and remain unconfirmed; treat the payload's field-level shape as needing a live-payload check at apply time, not the fact that `edited` fires at all.

Because `edited` is excluded from the default trigger set, a workflow declared as a bare `on: pull_request:` (or one with an explicit `types:` list that omits `edited`) does not re-run when GitHub silently retargets a PR's base. This next consequence is derived from the two confirmed facts above, not a directly quoted GitHub statement: the PR's checks tab keeps showing its last result, computed against the old base — so a reviewer, or an automated merge gate, can see a green check on a PR whose actual diff against its current base was never tested. This derivation is supported by GitHub's required-status-checks documentation, which describes checks as keyed to the latest commit SHA on the PR rather than to its base branch or diff ([GitHub Docs: Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks)) — a check computed for a SHA before retargeting has no mechanism that would invalidate it when the base changes without a new commit. Given that CI is meant to be the sole merge authority for this engine's PRs, this is a real hazard, not a cosmetic one.

Fix: add `edited` to the workflow's `types:` list for the `pull_request` trigger, on whichever workflow file the target repository uses to gate PRs. Illustrative before/after of the trigger block only (apply the same change to the target repository's actual workflow file):

Before (default; misses retargeting):

```yaml
on:
  pull_request:
```

After (fixed):

```yaml
on:
  pull_request:
    types:
      - opened
      - synchronize
      - reopened
      - edited
```

A human can run these by hand before trusting the boundary, and an automated preflight can run the identical commands programmatically before starting an engine run. Replace `<ORG>`, `<REPO>`, `<BASE_BRANCH>`, `<MACHINE_USER_HANDLE>`, and `<RULESET_ID>` with real values at run time; none belong in any committed file.

### Identity invariants

| Invariant | Command | Expected result |
|---|---|---|
| Authenticated identity is the machine user | `gh auth status` | Reports logged in to github.com as `<MACHINE_USER_HANDLE>`, not the human operator's own account |
| Authenticated identity is the machine user (scriptable) | `gh api user -q .login` | Outputs `<MACHINE_USER_HANDLE>` exactly |
| Machine user is not an Admin on the repo (primary check) | `gh api repos/<ORG>/<REPO> -q .permissions.admin` | `false`; works identically for organization-owned and personal-account repositories, needs only Metadata read, and requires no `<MACHINE_USER_HANDLE>` plumbing; reference: [GitHub Docs: Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository) |
| Machine user is not an Admin on the repo (corroborating fallback) | `gh api repos/<ORG>/<REPO>/collaborators/<MACHINE_USER_HANDLE>/permission -q .permission` | `write` (not `admin`); `maintain` maps to `write` and `triage` maps to `read` in this field's value space; reference: [GitHub Docs: Get repository permissions for a user](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user) |

Naming trap, verified against both endpoints above: the top-level string field is named `permission` and returns the string `"write"`. The boolean capability map on both endpoints (`.permissions` on the repository object, `.user.permissions` on the collaborator-permission response) uses the key `push`, not `write`, to represent write access — there is no `.permissions.write` key at all. A check written against `.permissions.write` will never match anything and will silently fail closed or open depending on how the missing key is handled; use `.permissions.push` / `.permissions.admin` for the boolean form and `.permission` for the string form, and never mix the two. Both responses also expose a `role_name` field; its literal value for a plain Write role is undocumented and inconsistent across GitHub's own published examples, so it must not be hard-coded into any check.

### Ruleset invariants

| Invariant | Command | Expected result |
|---|---|---|
| Ruleset exists on the base branch and is Active | `gh api repos/<ORG>/<REPO>/rulesets -q '.[] \| {id,name,target,enforcement,source_type}'` | An entry with `target: "branch"` and `enforcement: "active"`, matching the ruleset created in Section 4; reference: [GitHub Docs: Get all repository rulesets](https://docs.github.com/en/rest/repos/rules#get-all-repository-rulesets) |
| Pull-request review is required with at least 1 approval (primary check — effective rules for this branch) | `gh api repos/<ORG>/<REPO>/rules/branches/<BASE_BRANCH> -q '.[] \| select(.type=="pull_request") \| .parameters.required_approving_review_count'` | An integer >= 1. This endpoint returns GitHub's own computed effective rules for the given branch — it performs the ref-pattern matching server-side and includes rules inherited from organization-level rulesets ("All active rules that apply will be returned, regardless of the level at which they are configured"), so it is the recommended primary check rather than re-deriving effective state from the raw ruleset list. It exposes no bypass information. Same Metadata-read cost as the row above; reference: [GitHub Docs: Repository rules](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch) |
| Pull-request review is required with at least 1 approval (corroborating check — this specific ruleset) | `gh api repos/<ORG>/<REPO>/rulesets/<RULESET_ID> -q '.rules[] \| select(.type=="pull_request") \| .parameters'` | Verified field name: `required_approving_review_count`, an integer >= 1. Sibling parameters on the same object: `dismiss_stale_reviews_on_push`, `require_code_owner_review`, `require_last_push_approval`, `required_review_thread_resolution`, `allowed_merge_methods` (values `merge`/`squash`/`rebase`), and an optional beta `required_reviewers`. Trap, verified: the rulesets-listing endpoint's `includes_parents` parameter defaults to `true`, so a naive `gh api repos/<ORG>/<REPO>/rulesets` call silently mixes in organization-level rulesets alongside the repository's own. Distinguish them via `source_type`, whose values are `Repository`, `Organization`, or `Enterprise` — filter to `source_type == "Repository"` (or explicitly pass `includes_parents=false`) when the goal is to confirm the specific ruleset built in Section 4, not any ruleset that happens to apply to the branch.

### The bypass-list gap (open, not machine-verifiable by this token)

This is the one invariant this runbook cannot close with a command. GitHub returns `bypass_actors` only to a caller with write access to the ruleset itself: "To prevent leaking sensitive information, the bypass_actors property is only returned if the user making the API request has write access to the ruleset" ([GitHub Docs: Repository rules](https://docs.github.com/en/rest/repos/rules)). Administration set to Read-only, which is already excluded from the engine's token per Section 3, is insufficient to satisfy that condition; a real-world report confirms the field is withheld under exactly this circumstance ([GitHub Community Discussion #152059](https://github.com/orgs/community/discussions/152059)).

The engine's token deliberately withholds Administration entirely (Section 3), and that exclusion is not incidental to this gap — granting the write access that would be needed to read `bypass_actors` would also let the engine edit or delete its own ruleset, which is precisely the boundary Section 1 exists to prevent. As a direct consequence, the "bypass list is empty" invariant cannot be verified by the engine's own identity under any token scope compatible with this runbook's own constraints.

An absent `bypass_actors` key is indistinguishable, from this caller's perspective, from a present-but-empty `[]` array — both read as "nothing here" to a token lacking write access to the ruleset. The preflight commands in this section must never treat an absent key as proof the bypass list is empty; doing so would silently defeat the exact invariant Section 4 depends on. `[unverified]`: whether a caller that DOES have write access sees `bypass_actors` as `[]` or as an omitted key when the list is genuinely empty was not confirmed in this pass — the cited discussion covers only the read-access-insufficient case.

OPEN DECISION, not yet resolved by this runbook: whether to (i) accept this as a permanent verification gap and rely on the human-performed check at ruleset-creation time in Section 4 plus periodic manual re-checks, (ii) mint a second, narrowly-scoped credential with ruleset write access used only for this one read — which reintroduces a version of the exact risk this gap is about, unless that credential is itself isolated from the engine's own process — or (iii) have a human, under their own admin credentials, run this specific check as a step outside the engine's own token. This runbook does not choose between them; whoever operationalizes the preflight must.

For reference, verified `bypass_actors` element shape, when it is returned: `actor_id` (integer or null), `actor_type` (one of `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team`, `DeployKey`, `User`), `bypass_mode` (one of `always`, `pull_request`, `exempt` — singular "pull_request").

Supplementary checks (useful, but not part of the invariants above):

- The fine-grained PAT's own granted permissions are not retrievable via any `gh api` call after the token is minted. This is now confirmed as a structural absence rather than an unverified gap: the `X-OAuth-Scopes` response header, which historically exposed a classic PAT's scopes, applies only to classic and OAuth tokens, not fine-grained PATs. The related `X-Accepted-GitHub-Permissions` header reports what a given ENDPOINT requires to succeed, not what permissions the calling token actually holds — the two must not be conflated. Confirming a fine-grained PAT's granted permissions remains a manual check against its detail page under the machine user's own Settings > Developer settings.
- `[unverified]`: whether "Do not allow bypassing the above settings" (Section 4) surfaces as its own distinct field in the rule's `parameters`, or is only implied by an empty `bypass_actors` array combined with an active enforcement status — no docs sentence found confirms or denies this; check a live `gh api repos/<ORG>/<REPO>/rulesets/<RULESET_ID>` response at apply time.
- The legacy `gh api repos/<ORG>/<REPO>/branches/<BASE_BRANCH>/protection` endpoint reports classic branch-protection-rule state; its relationship to a ruleset-based setup was not re-verified in this pass. Treat the ruleset-based checks above as authoritative and this endpoint as optional/exploratory only.

## 8. Failure and rollback

**Machine user is locked out** (lost credentials, lost 2FA device, account flagged): the engine simply cannot push or open PRs — a fail-closed, safe state; no invariant from Section 7 is put at risk by this failure. Recovery is an ordinary GitHub account-recovery process on the machine user's own account (needs confirmation at apply time: the exact current recovery flow and URL, GitHub's account-recovery UI changes independently of this runbook). If the account is unrecoverable, create a new machine-user account, repeat Sections 2 and 3 for it, remove the old account's repository access, update the environment variable the engine reads its token from, and re-run Section 7 in full before resuming any engine run.

**PAT expires mid-run**: the engine's `git push` and `gh api` calls begin failing with an authentication error. This is also fail-closed — nothing merges and nothing bypasses, the run simply halts on push/PR operations. Recovery: mint a replacement fine-grained PAT (Section 3) — proactively, before the old one's expiry if possible — update the environment variable the engine reads from, and resume. No role or ruleset change is needed, since the underlying identity did not change.

**PAT is minted without the "Actions" permission at Read** (row (d) of Section 3's table is skipped, or an operator mistakenly grants "Commit statuses" instead, per an earlier draft of this table): pushes and PR creation both still succeed, since those depend on Contents and Pull requests (Section 3), not Actions. What breaks is narrower and easier to miss than the fail-closed modes above — the ship stage's `gh run list` / `gh run view` calls (`mitosis.js:4596`) return an authorization error against the Actions Workflow Runs API, so the engine never resolves a CI run id or never reads a terminal conclusion. This is a materially different, and in one sense worse, failure shape than a locked-out account or an expired token: the merge boundary itself is completely unaffected — self-approval is still blocked, the ruleset still requires a PR and an approval, and nothing can bypass it — but the engine silently loses the one signal (CI GREEN vs CI RED) it uses to decide whether a PR is safe to hand to a human, rather than being stopped outright by an authentication failure at the point of the git/PR operations covered above. Recovery: confirm the PAT's granted permissions on the machine user's own Settings > Developer settings > token detail page (Section 7's supplementary checks note this cannot be read back via `gh api`), add Actions at Read-only if it is missing, and re-run Section 7's identity checks before resuming any engine run.

**Ruleset must be temporarily relaxed** (for example, an emergency change a human needs to push straight to the base branch): do not accomplish this by adding any account to the bypass list — that risks becoming a standing hole if anyone forgets to remove it afterward. Instead, a human, authenticated with their own admin credentials (never the machine user's), temporarily changes the ruleset's Enforcement status from Active to Disabled, performs the single emergency action directly, and immediately restores Enforcement to Active. Record the exception window (start time, end time, reason, who performed it) somewhere durable, since this is precisely the kind of exception the ruleset exists to make rare and visible rather than to prevent outright. Immediately after restoring enforcement, re-run every command in Section 7 to confirm `enforcement` reads `active` again and `bypass_actors` still reads `[]` before resuming any engine run.
