EXPLANATIONS ESTABLISHED IN CHAT THAT THE NEXT SESSION SHOULD NOT RE-DERIVE:
- Two kinds of blocked. Blocked-but-buildable (parent built|awaiting|done) is built ahead TODAY on the parent's checkpoint tip with its PR deferred — that is not a capability this work adds. Blocked-and-stuck (parent parked, cap full, lease conflict) has nothing to do. Quiescence = only the second kind plus units awaiting a human merge remain.
- Why early-open PRs fail, sharper than 0066 stated it: squash-merge lands a parent's content under a NEW sha, so a published child branch MUST be restacked when its parent merges, and restacking a published branch is a force-push. EVERY open-early scheme therefore requires force-pushing published refs (or supersede-with-a-new-PR churn that loses review comments). The blocker is mechanical, not stylistic.
- Merge-blocking while open DOES exist and works (a required "stack-guard" status check that stays red until every parent PR merges; draft PRs; a depends-on bot). It is not the obstacle — the force-push requirement above is. Also load-bearing: with superset diffs, merging a child first would silently ship its unreviewed parent's content, so such a guard would be mandatory rather than optional.
- Durability inventory: checkpoint refs on origin, open PRs, and merged work all survive process exit AND a fresh clone. .mitosis/run.json and the per-MSP .plan.md artifacts are gitignored and MACHINE-LOCAL — they do not survive a fresh clone/worktree/CI workspace (:4329 says so). Losing them costs cached plans, not built work, which is exactly why the spec demotes the journal to a hint.
- Exit is checkpointing, not cancelling: the run's identity is durable state (manifest + checkpoint refs + PR state), and the process is a worker that advances it.
