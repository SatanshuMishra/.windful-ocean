=== SECTION 1, LAYOUT ===
~/.claude/ is the mutable root - Claude Code owns it and writes .claude.json, backups/, projects/, sessions/ and plugins/ into it, so only SUBTREES can be release-pointed.
  releases/<sha>/            immutable, built by `git archive <sha> .claude`
                             holds skills agents lib workflows hooks rules docs notes sounds CLAUDE.md keybindings.json
  current -> releases/<sha>  THE pointer
  skills -> current/skills, agents -> current/agents, one link per entry, ALL routed through current
  settings.json              REAL file, never promoted (see 0270)
  local/                     declared live-only overlay
  plugins/ sessions/ projects/ .claude.json backups/   runtime state, never promoted
  LIVE                       receipt {ref, sha, built_at, promoted_at, previous}
The `current` indirection is load-bearing: linking each entry straight at a release makes promotion N renames instead of one. Two-hop resolution is evidenced, not assumed - nested hops were measured to traverse.
Live-only strays are ADOPTED into the repo: the 4 live-only hook files and the untracked rules/context7.md (plain instructions, no secret). local/ is reserved for genuinely machine-specific files. plugins/ stays live-only forever.

=== SECTION 2, THE PROMOTE VERB ===
Idempotent, one entry point. Resolve ref -> sha; if releases/<sha> is absent build it (git archive into <sha>.tmp, then rename); VALIDATE; swap; write LIVE; GC to the last N releases, never deleting current or its predecessor.
The swap is create-then-rename, NOT `ln -sfn`: `ln -s releases/<sha> current.tmp && mv -f current.tmp current`, because rename(2) replaces a symlink atomically while ln -sfn unlinks then symlinks and leaves a window with no pointer. The live permission set grants Bash(ln -sfn:*) and so encodes the wrong form - it needs updating.
Idempotence comes from comparing realpath(current) against releases/<sha> before swapping.

=== SECTION 3, ENFORCEMENT ===
LIVE == main. STAGING == everything else. Branch work never reaches a running agent; merging IS feature completion, so "sync on feature completion" becomes "converge live to main".
One verb, three call sites: SessionStart (converge), Stop (converge), mitosis Ship (promote after merge). It is a CONVERGENCE CHECK, not an event handler - an event can be missed when a process dies or a merge happens from the web UI; comparing desired-ref against LIVE cannot. The teeth are that SessionStart and Stop are HOOKS: the harness runs them, so the model cannot decline them. That is what makes the sync never a suggestion.
A drift report is surfaced into session context when live != main at start, so divergence is visible rather than silent.

=== SECTION 4, SAFETY ===
Validate the candidate release BEFORE the swap: every entry the live links expect exists; hook paths registered in settings.json resolve inside the release or local/; hook scripts are executable and pass node --check / bash -n; JSON parses. Failure = no swap, loud drift report, live stays on the last good release.
Rollback swaps current to LIVE.previous - a rename, never a rebuild, because releases are immutable and retained.
NAMED INVARIANT: the promote verb and the SessionStart hook must live OUTSIDE releases/ at a stable absolute path. A bootstrap self-hosted in the thing it promotes means a bad release breaks the machinery that would roll it back, in every future session. This is the one way the design can brick the environment and belongs in the SPEC as an invariant, not an implementation detail.

=== SECTION 5, settings.json (full rationale in 0270) ===
Excluded from releases entirely, because a symlinked settings.json is followed and written through - the release would be mutated in place and writes made while it is live would be stranded there on a swap.
Repo tracks the DECLARED config (hooks, permissions, env). Live is the EFFECTIVE config Claude Code writes into. Promotion recomputes live = repo-owned keys plus preserved live-owned keys (model, pluginConfigs, extraKnownMarketplaces, plugin enablement, permission grants), driven by an ownership manifest. Unknown or newly-appearing keys default to LIVE WINS and are flagged, never silently dropped.
CAPTURE (live -> repo) is a separate explicit verb and the ONLY direction that can leak, so it runs through the leak gate before touching tracked content.

=== SECTION 6, MIGRATION ===
The cutover is itself a hot swap, which is the hazard. Order: build and validate with ZERO live change, then swap every entry link in one pass, in a session doing nothing else. Any failure means nothing moved.

=== SECTION 7, OUT OF SCOPE ===
plugins/, sessions/, projects/, .claude.json and backups/ are runtime state and are never promoted.

=== THE UNMEASURED QUESTION, handled honestly ===
Immutable releases plus one rename guarantee no FILE is ever read half-old. They do NOT guarantee cross-file consistency: if resolution is live, a session could hold release A's skill roster while reading release B's bodies. Retention does not fix this, because reads route through the pointer rather than a pinned release. The mitigation is TIMING - promote at SessionStart and between MSPs at Ship, never mid-MSP - and the measurement, once taken, tells us whether even that is needed. Do NOT write the SPEC as though this is solved.
