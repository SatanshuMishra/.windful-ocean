=== STACKED-PR RESEARCH (researcher, ~93k tokens; transcript will NOT survive) ===
GitHub shipped NATIVE stacked PRs to PUBLIC PREVIEW on 2026-07-30, six days before this session and after the assistant knowledge cutoff. https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/ and https://docs.github.com/en/pull-requests/get-started/about-stacked-prs . Two distinct paths exist: the decade-old CONVENTION (PR B base = PR A head, plain gh pr create --base / gh pr edit --base, GA for years) and the PREVIEW PRODUCT (gh extension install github/gh-stack, giving gh stack init/add/submit/view/rebase/merge/sync). Preview is "subject to change"; no cross-fork stacks; merge-queue support was still rolling out at launch.
THE CORE HAZARD. Squash-merge replaces N commits with one new commit whose SHA matches nothing on the child branch, leaving a stale merge-base so a plain rebase replays merged content as phantom conflicts. Structural to Git, not a GitHub defect. GitHub's own troubleshooting doc concedes server-triggered rebases produce UNSIGNED commits: https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-stacked-pull-requests . Independent reports (InfoQ, byteiota) say squash and rebase merges break GitHub's stack identity tracking and need a manual gh stack rebase. This is what decision 0265 removes at the root.
OTHER COSTS. Merging a stack requires the ASYNC merge API - "the legacy pull request merge endpoints can't merge a stack" - which puts .claude/lib/superpowers-parallel/gh-merge-shim.mjs (357 lines) in scope. CI re-runs per stack level; GitHub exposes stack.position and stack.size to gate expensive jobs (https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/optimizing-ci-for-stacked-pull-requests).
THE ARGUMENT AGAINST, and why it does not apply. https://newsletter.pragmaticengineer.com/p/stacked-diffs argues small teams gain little from stacking. That argument is entirely about unblocking parallel HUMAN reviewers, which a solo owner does not have. The motive here is different - keeping the ENGINE producing while a PR waits on a human merge - and the cited objection does not touch it. Do not let a future session mistake this for a reason to abandon (c).

DESIGN CONSTRAINT for SPEC A: Claude Code WRITES settings.json itself via permission prompts, model selection and plugin toggles, so it is a TWO-WAY surface and a one-way staging-to-live promotion would silently clobber it.
DESIGN LEVER for SPEC A: CLAUDE_CONFIG_DIR is the only documented config-directory override, read once at startup, and it relocates everything under ~/.claude including credentials, history and sessions - so using it for a staging session fragments session state, which is a real cost to weigh. Symlink resolution behaviour (realpath vs as-is) is NOT documented and must be settled empirically the same way the import question was.
DESIGN PRINCIPLE proposed, not yet ratified: make sync a CONVERGENCE CHECK, not an event handler. An event trigger can be missed (process died, merged from the web UI); a reconciliation that compares desired ref against the live pointer at every session start cannot. Candidate shape is Capistrano-style immutable release dirs plus an atomic ln -sfn pointer swap, with SessionStart, Stop and mitosis Ship all calling the same idempotent promote verb.
